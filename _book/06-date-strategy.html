11  날짜 전략

11.1 target date와 actual capture date

이 파이프라인에서는 두 날짜를 구분한다.

target_date
사용자가 GEID에 요청하는 기준 날짜다.
actual_capture_date
GEID 로그에 기록된 실제 이미지 타일의 촬영일이다.

두 날짜는 다를 수 있다. 더 중요한 점은, 하나의 target_date 요청 결과 안에서도 실제 타일 촬영일이 여러 개일 수 있다는 것이다.

11.2 generate_target_dates()

target date 목록은 main.py에서 생성하는 것이 좋다.

Note날짜 범위는 main.py의 정책

start_year, end_date, target_months 같은 날짜 범위 설정은 운영 정책이다. core.py는 이 범위를 직접 해석하지 않고, 이미 만들어진 target_dates 리스트만 받는다.

예시 함수:

def generate_target_dates(start_year: int, end_date_str: str, target_months: list, day: int = 15) -> list:
    ...

예시 사용:

target_dates = generate_target_dates(
    start_year=args.start_year,
    end_date_str=args.end_date,
    target_months=[5, 8, 11],
)

이 함수의 리턴값은 문자열 리스트다.

예를 들어 start_year=2021, end_date_str="2022-12-31", target_months=[5, 8, 11], day=15라면 다음과 같은 값이 만들어질 수 있다.

[
    "2021-05-15",
    "2021-08-15",
    "2021-11-15",
    "2022-05-15",
    "2022-08-15",
    "2022-11-15",
]

end_date_str="today" 또는 "now"를 쓰는 구현에서는 마지막에 current imagery 요청을 위한 "current"를 추가할 수 있다.

[
    "2021-05-15",
    "2021-08-15",
    "2021-11-15",
    "...",
    "current",
]

초기 구현에서는 --start_year와 "today" 조합만 써도 된다. 다만 장기적으로는 --end_date도 CLI 인자로 받는 편이 운영 문서에는 더 명확하다.

11.3 download_roi()의 target_dates 인자와 연결

core.py는 시작일과 종료일을 직접 받지 않는다.

대신 main.py에서 생성한 날짜 목록을 받는다.

pipeline.download_roi(
    roi_gdf=roi_gdf,
    roi_name=roi_name,
    output_sub_dir=output_sub_dir,
    target_dates=target_dates,
    zoom=args.zoom,
)

즉 generate_target_dates()의 리턴값이 download_roi()의 target_dates 인자로 그대로 들어간다.

역할을 나누면 다음과 같다.

main.py
  start_year, end_date, target_months를 해석
  → target_dates 리스트 생성

core.py
  target_dates 리스트를 순회
  → 각 target_date마다 GEID CLI 호출

core.py는 날짜 범위를 계산하지 않는다. 이미 만들어진 target_dates를 받아 실행만 담당한다.

11.4 실제 촬영일 기준 저장

core.py는 GEID 로그를 읽어서 각 패치를 실제 촬영일 폴더에 넣는다.

patches_{site_id}/
├── 2021-05-11/
├── 2021-04-29/
└── Current_Default/

이 구조는 여러 target date를 요청했을 때 같은 실제 타일이 중복 저장되는 것을 줄이기 위한 설계다.
